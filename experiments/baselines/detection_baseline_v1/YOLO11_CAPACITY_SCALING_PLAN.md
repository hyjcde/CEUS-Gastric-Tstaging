# YOLO11 Capacity Scaling Plan

## 文档目的

这份文档专门回答一个问题：

- 当前检测 baseline 偏低时，下一步应该先放大 `YOLO11` 模型规模，还是直接改网络结构？

当前建议是：

- 先做容量扩展实验
- 第一优先级先跑 `YOLO11l`
- 先不要急着自定义改网络结构

原因不是“结构改动没用”，而是当前证据还不够支持把主要精力投入到复杂结构设计上。

## 当前已有证据

当前已经完成 3 个 `YOLO11` 规模的正式评估：

| model | internal mAP50-95 | prospective mAP50-95 | external mAP50-95 |
| --- | ---: | ---: | ---: |
| `YOLO11n` | `0.406` | `0.392` | `0.359` |
| `YOLO11s` | `0.392` | `0.393` | `0.360` |
| `YOLO11m` | `0.418` | `0.400` | `0.361` |

从这些结果可以得到 3 个结论：

1. `n -> m` 后内部集是有提升的，说明模型容量不是完全没用。
2. 前瞻集只有小幅提升，说明放大模型收益已经开始变缓。
3. 外部集几乎不变，说明主要瓶颈不只是容量，还存在明显域偏移。

这和前面的子集分析是一致的：

- 内部不同年份之间存在分布差异，尤其 `2019` 更难。
- 外部不同来源之间存在明显差异，不是所有外部数据都同样困难。

## 为什么先做大模型，而不是先改网络

先做更大的现成模型，科研上有 3 个好处：

1. 变量更少。  
   这一步主要回答“当前瓶颈里，模型容量占多大比例”。

2. 解释更干净。  
   如果 `YOLO11l` 就能稳定提升，那说明先前模型确实偏小；如果提升很有限，再去做结构改动才更有说服力。

3. 复现实验成本更低。  
   改 `n / s / m / l / x` 属于标准缩放，和自定义结构相比更容易重复、横向对照也更公平。

## 当前推荐路线

### 第一阶段：先验证容量瓶颈

优先级如下：

1. `YOLO11l`, `imgsz=640`
2. `YOLO11l`, `imgsz=960`
3. 视结果决定是否继续 `YOLO11x`

其中：

- `YOLO11l, imgsz=640` 是第一步，因为它只改模型规模，最适合做干净对照。
- `YOLO11l, imgsz=960` 是第二步，因为病灶定位对局部细节更敏感，只放大模型不一定足够。

### 第二阶段：根据结果决定方向

如果出现下面这些情况，后续策略应该不同：

1. 如果内部明显提升，但外部几乎不升  
   说明主要问题是域偏移，下一步应该优先做数据策略和泛化策略，而不是继续无脑放大模型。

2. 如果内部、前瞻、外部都稳定提升  
   说明容量仍然是核心瓶颈，可以继续尝试 `YOLO11x`。

3. 如果几乎都不提升  
   说明当前瓶颈不在模型大小，改网络结构也未必是高回报路径，应该回到错误分析和数据分布问题。

## 建议的实验矩阵

建议按照下面顺序跑：

| stage | config | 目的 |
| --- | --- | --- |
| 1 | `YOLO11m + 640` | 作为当前容量基线 |
| 2 | `YOLO11l + 640` | 验证更大模型是否稳定增益 |
| 3 | `YOLO11l + 960` | 验证更高分辨率是否改善定位 |
| 4 | `YOLO11x + 640` | 只有在第 2 步明显有效时再考虑 |

## 每一步重点看什么

不要只看总分，至少要固定看下面这些维度：

1. `internal_test`
2. `prospective_test`
3. `external_test`
4. 内部按年份子集
5. 外部按来源子集
6. 具体失败案例图

特别需要盯住：

- `2019` 内部年份子集
- 外部困难来源子集
- 漏检、多框、定位偏差这三类失败模式

## 什么时候才值得改网络结构

当满足下面任意一种情况时，改网络结构才更值得：

1. `YOLO11l` 和 `YOLO11x` 的提升都很有限。
2. 错误分析显示某种失败模式很集中，比如小病灶持续漏检、多灶场景经常少检、边界模糊时框偏差明显。
3. 你已经能证明问题主要不是数据域偏移，而是特征表达能力不够。

在那之前，更推荐先做：

- 模型规模扩展
- 输入分辨率扩展
- 难例可视化与错误归因

## 当前执行决定

本轮先执行：

1. 新增 `YOLO11l` 对照配置
2. 启动 `YOLO11l, imgsz=640` 训练

对应配置文件：

- `configs/detection/yolo11/baseline_lesion_holdout_cropui_yolo11l.yaml`

## 后续判定标准

如果 `YOLO11l` 相比 `YOLO11m`：

- `internal_test` 提升明显，且 `2019` 子集也改善  
  说明放大模型是有效方向。

- 只提升内部，不提升外部  
  说明应转向泛化和数据策略。

- 提升极小  
  说明不应该继续把主要资源投到更大模型上。
